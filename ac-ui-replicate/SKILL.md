# ac-ui-replicate — 空调节能监控平台 UI 复刻技能

## 目标
任何 agent 平台装上本 skill 后，遇到可视化开发需求（监控大屏、设备管理、表格列表、工艺图、权限管理等），按本 skill 的规范一键生成与「空调节能监控平台」完全同款的 UI——仅业务逻辑不同。

## 核心资产（references/ 目录，按需读取，勿全量读入）
1. `DESIGN.md` — **主规范（最重要）**：YAML 设计 token（颜色/字体/圆角/阴影，浅暗双主题）+ 布局骨架规则 + 组件契约 + 页面模式库 + 交互规则（12 项红线）+ Do & Don't + 通用模块模板（权限/表格筛选/状态徽章）
2. `DESIGN-tailwind.css` — 可直接 import 的 Tailwind v4 token 文件（@theme 块）
3. `knowledge/01-framework.md` — 框架层细节（路由表/DOM 骨架树/token 全表/主题切换）——DESIGN.md 不够时查此文件
4. `knowledge/02-pages.md` — 12 个页面模块逐一分析 + 9 个页面模式库（列表页/详情页/表单弹窗/图表页/工艺图模式）
5. `knowledge/03-components.md` — 42 个 shadcn 组件契约 + 业务组件 + 图表封装 + 工艺图 SVG 模式
6. `knowledge/04-interactions.md` — 16 页线上实测交互态（下拉/分页/表格/悬停精确值）
7. `regression-checklist.md` — **回归防护清单（必须遵守）**：历次已修复 bug 逐条登记；修 bug 前先查是否「旧病复发」，修完后登记新条目；**任何 UI 变更交付前必须逐条跑完全部回归项，全绿才允许收尾**——防「修新 bug 把旧 bug 改回去」
8. `credentials.enc` + `decrypt-credentials.mjs` — 参考站账号密码（AES-256-GCM 加密密文）。**密钥位置由管理员私下提供，不在本 skill 包内**（分发 zip 给别人拿不到密码）。需要登录参考站时：`node references/decrypt-credentials.mjs <密钥文件路径>`（默认输出到临时文件并只打印文件路径；`--print-account-only` 只出账号不出密码）
9. `ui-diff/`（随包分发的验收工具，依赖 node + playwright（浏览器 channel msedge），见 `ui-diff/README.md`）：`run.mjs`（双站 DOM 全指标对比）、`save-state.mjs`（我方线上飞书 SSO 登录态保存）、`overflow.mjs`（4 视口溢出检查）；cable 登录凭证走环境变量 `CABLE_USER`/`CABLE_PASS`（经 decrypt-credentials.mjs 解密获得，包内禁存明文）
10. 另有 `DESIGN-tokens.yaml` / `tokens.json`（token 机器可读版，供 `mcp/ac-ui-design.mjs` 查询）、`check-drift.mjs`（目录漂移巡检脚本）、`mcp/`（ac-ui-design.mjs 轻量 token 查询 server，形态演进中期项，当前未接入 CodeM）——按需使用

## 工作流（新页面/新项目开发）
1. **识别需求**：用户描述业务（如「做水泵监控页」）→ 映射到页面模式库中最近似的模式（列表页/详情页/图表页/工艺图/权限管理）
2. **读规范**：读 `DESIGN.md`（一次通读，~10K token）——这是唯一必读文件；细节再按需查 knowledge/
3. **搭骨架**：按 DESIGN.md「布局骨架规则」搭 AppShell（侧栏 256px（w-64）↔ 折叠 80px（w-20）+ 顶栏 h-14 + 内容区）；引入 `DESIGN-tailwind.css`（SKILL.md 与 DESIGN.md 数值冲突时一律以 DESIGN.md 为准）
4. **组装页面**：按页面模式库模板组装；组件按「组件契约」用 shadcn + 规定 class；文案/交互遵守 12 项红线（下拉缺省值不空、分页完整形态、bit 型开关分渲染等）
5. **生成时自查表（硬性环节，不可跳过；纯静态对照，不依赖浏览器，30 秒完成）**：组装完成后、声明交付前必须逐项打勾，任一项不符先改再交付：
- **token 8 项**（对照 `DESIGN-tailwind.css` 逐项核对本页实际生效值）：--primary、--ring、--radius、--background、--card、--border、--brand-accent、--sidebar-primary
   - **骨架 10 项**（对照 DESIGN.md 布局骨架规则逐项核对 class）：① 侧栏展开 256px（w-64）↔ 折叠 80px（w-20）② 顶栏 h-14 + 底边框 ③ 卡片 rounded-xl + border-card-border + shadow-sm ④ 内容区 padding ⑤ 品牌区形态（logo 尺寸/内距）⑥ 菜单项高/padding/选中态 ⑦ 主题变量 --radius 生效 ⑧ hover 反馈（elevate 体系/按钮上浮 0.18s）⑨ 下拉/分页/表格核心 class 契约 ⑩ 暗色区块绝对色值（ac-dark-page 等）
6. **接入业务**：替换数据层（API/轮询间隔/SSE），UI 结构不动
7. **强制验收闭环（硬性要求，不可跳过）**：任何 UI 页面生成/修改后，必须自动验收；**交付声明必须附带验收表（30 项逐项 Pass/Fail），未出示验收表不得声明完成**：
   - **三级降级验收路径**（按可用环境从高到低选，验收表须注明所用级别）：
   1. **ui-diff 自动对比**：有 playwright 环境时跑 `node ui-diff/run.mjs`（双站 DOM 全指标 diff；我方线上登录态缺失先跑 `node ui-diff/save-state.mjs`）
   2. **playwright 手抓**：无 ui-diff 可跑时，用 playwright 手抓 computed style 对照 DESIGN.md token 逐项核对（侧栏/顶栏/卡片/主色/圆角/阴影）
   3. **纯静态 token/class 对照表核对**：无浏览器环境时，把生成代码的 CSS 变量值与 `DESIGN-tailwind.css`、骨架 class 与 DESIGN.md 布局规则逐项列表核对
   - **无凭证时**（参考站登录凭证/密钥不可得）：允许跳过参考站对比，仅做静态核对，但**必须在验收表中标注「未做参考站对比（无凭证）」**
   - **交互态自查**：按 12 项红线清单逐项过（下拉缺省值/选项清单/分页完整形态/翻第 2 页/悬停/按钮数）
   - **响应式溢出**：有环境时跑 `node ui-diff/overflow.mjs`（4 视口检查）
   - **回归清单**：逐条跑 `regression-checklist.md` 全部条目，全绿才算完成
   - 验收发现的差异：修复 + 回写 DESIGN.md + 登记/更新回归项；**Fail 项须同时把「为什么生成时自查表没对照到」记入 regression-checklist.md**（补进自查表覆盖面）

### 目录结构变更流程与边界（先梳理→规划→整理，硬性顺序）

- 任何涉及目录新建/迁移/改名/清理的操作，**必须按三步走，禁止跳步直接动手**：
  1. **先梳理**：list_dir 全盘巡检当前工作空间现状（散落文件、旧目录、乱放点），不动任何东西
  2. **再规划**：基于巡检结果出目录方案，**报请求人确认定稿后才动手**
  3. **后整理**：按定稿方案执行迁移/清理，每步验证（迁移后核对文件数/路径可达）
- **严禁越界**：所有文件操作仅限当前工作空间（会话主工作目录 + 显式授权目录），绝不触碰其它工作空间、其它项目或系统目录；破坏性操作（rm -rf、批量改名等）即使在工作空间内也须先报批
- **复查机制（防漂移，触发式为主 + 低频例行）**：
  - 触发式：发现根目录/项目目录出现散落文件、或在非规定位置新建目录时，立即巡检并按归位规则整理
  - 例行：每月首个工作会话（或大版本交付后）list_dir 巡检一次，对照目录规范检查漂移，发现即归位并回写教训

## 讨论 / 头脑风暴 / 碎片化需求工作流（g_133，2026-09-21）

**触发识别（自动，无需用户强调「调用技能」）**：出现以下任一信号即进入本流程，**不急于写码**：

- **讨论信号**：问「能不能 / 要不要 / 如果 / 可不可以」、征询意见（「你觉得呢」「哪种好」）、聊某个页面/功能的痛点或改进想法
- **碎片化信号**：一句话突然带出功能想法（如「诶对了，那个页面要是能 XXX 就好了」「突然想到个事」）、东一句西一句补充需求、对已有方案片段式修正
- **头脑风暴信号**：明确说「讨论一下 / 想一想 / 头脑风暴 / 梳理一下 / 帮我规划」
- **排除信号**（不触发，直接执行）：明确的祈使指令（「把 X 改成 Y」「跑一下」「部署」「直接做」）、纯查询/排障、用户明确说「不用确认」

**歧义降级策略**：拿不准是「讨论」还是「直接做」时，一律按讨论处理（先梳理方案再确认）——宁可多问一句，不可直接动代码（红线 1）。进入讨论流程时**主动告知**：「已进入方案讨论模式，方案文档：docs/plans/<主题>.md，todo 已建」——让用户可见流程已被触发，而不是默默进行。

1. **进入方案模式**：调用 `brainstorming` 技能走「分类→澄清→2-3 候选方案→分节设计」流程；**HARD-GATE：方案获批前不写实现代码**（红线 1）
2. **落盘方案与计划文档**：`docs/plans/<主题>.md`（无则创建）——**工作空间即项目隔离边界**（2026-09-21 请求人修订：项目通过 CodeM 不同工作空间隔离，不在目录层再按项目名分仓），本工作空间讨论的即本项目内容。固定结构：
   - **目标与背景** / **需求碎片池**（东一句西一句的原始想法逐条登记，标日期）/ **候选方案对比** / **当前方案（版本号 vN）** / **todo 清单** / **历史方案归档** / **修订记录**
**单文档迭代原则（2026-09-21 请求人补充，硬性）**：一个工作空间（= 一个项目）内一个主题**始终只有一份方案文档**（`docs/plans/<主题>.md`），在做的过程中突然想起的事情、颠覆性的新想法、讨论内容一律**合入这一份**反复迭代：
- **严禁**为同一主题新建第二份方案/计划文件，严禁产生「方案 v2.md」「方案-新.md」「XX计划(1).md」之类的版本文件——演进只体现在同一文件内的版本号与修订记录
- **颠覆原方案 = 更新这份文档**，不是另起炉灶。按颠覆程度两档处理（2026-09-21 请求人补充）：
  - **常规演进**：当前方案重写 + 旧版移入文内「历史方案归档」节（保留可追溯）
  - **颠覆性大**：可直接**删除旧方案主体重新讨论**，只留一行「vN 于某日废弃，原因：xxx」——不必保留完整历史，文档清爽优先
- 新会话/隔了多久再聊同一主题，先在本工作空间 `docs/plans/` 下找既有文档**续写**，找不到才新建
- **新项目 = 新工作空间**（请求人实际隔离方式，2026-09-21 修订）：项目间由工作空间天然隔离，勿在本工作空间写其他工作空间（项目）的方案；仅当同一工作空间确需承载多项目时，才经请求人确认后按项目名加子目录分仓
- 实现过程中边做边冒的新需求：直接更新该文档的需求碎片池与 todo，并同步修正已产出内容（同一份真相源）

3. **持续自动更新（每次讨论后必做，不等请求人催）**：
   - 新想法 → 追加进需求碎片池；影响方案的 → 同步更新当前方案与 todo（会话内用 task_create/task_update 实时维护）
   - **方案被推翻：不删除**——移入「历史方案归档」节，标注推翻原因、日期、被哪个版本取代；当前方案版本号 +1。讨论方案的演进历史是后续决策依据，与「确认有错的资料」区分（后者才走错误资料四步替换流程）
   - 每次更新后在修订记录追加一行（日期 + 变更摘要）
4. **收口确认**：讨论收敛后主动汇报「当前方案 vN 全貌 + todo 快照」，请请求人确认后才进入实现；确认后用 `writing-plans` 技能出实施计划

### 项目记忆沉淀（memory，2026-09-21 请求人补充，硬性）

对话/讨论内容必须**迭代沉淀**到项目工作空间对应目录，让每个项目拥有自己的记忆系统：

- **位置**：`docs/plans/MEMORY.md`——**工作空间（= 项目）一份**记忆文件（2026-09-21 请求人修订：项目由工作空间隔离，记忆不按项目名分目录），与方案文档同目录，随 git 迁移
- **沉淀什么**：请求人对话中说出的——关键决策与理由、偏好与禁忌（「不要 XX」「我喜欢 XX 形态」）、踩坑与修正、方案变更结论、验收标准。**只记结论性内容，不记过程流水**

- **单文档迭代**：同一项目始终只有这一份 MEMORY.md，反复迭代更新；颠覆性内容可删旧条目重写
- **新会话/换电脑怎么用**：开始本项目任何工作前**先读** `docs/plans/MEMORY.md`（不存在则随首次讨论自动创建）——记忆驱动，不靠用户复述背景
- **新项目 = 新工作空间**：该工作空间首次讨论时自动创建 MEMORY.md，各工作空间记忆互不混（多项目共存一个工作空间的例外同上：须请求人确认后才加子目录）

## 自迭代机制（发现差异必须回写）
- **错误资料必须替换，禁止保留（2026-09-21 g_129 设立，请求人同日修订流程顺序，防大模型幻觉与混乱）**：
  - 发现已归档资料（DESIGN.md / knowledge / regression-checklist / token 表等）内容疑似有错时，处理流程固定为四步「**先测 → 再改 → 改后再测 → 没问题再删**」：
    1. **先测**：实测复测，确认旧内容确实有错，同时得出经验证的正确做法
    2. **再改**：把正确内容写入资料（替换或并列标注）
    3. **改后再测**：按新内容实际执行/生成验证，确认正确可用
    4. **没问题再删**：验证通过后，才删除旧错误内容 + 补修订记录
  - **严禁跳过测试直接写入新结论；严禁在正确内容未经实测验证前删除旧内容**——必须保证任何时刻资料里都有已验证的内容，不留未验证真空期
  - **严禁长期保留已确认不符的旧内容**——验证通过后旧错误内容必须删除，不得双份并存（错误内容留在资料里会导致后续生成时被错误规范误导，是幻觉源）
  - 修订边界同红线 4：仅限补充与澄清，删除/弱化已确认条目须请求人明确指示

- 生成的页面被用户/自动对比发现与参考站不一致时：把差异项回写进 `DESIGN.md` 对应章节（token 表/组件契约/红线清单），并附「修订记录：日期 + 来源」
- 禁止只改代码不回写规范——规范是唯一真相源
- 新沉淀的交互规则同步更新本 skill 的 references（保持单一来源）
